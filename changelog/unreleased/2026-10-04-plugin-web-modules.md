# A plugin ships web modules that join the web app's module tree

- **Date:** 2026-10-04
- **Type:** feature
- **Scope:** `web`, `server`, `tooling`
- **Breaking:** yes — `ChatModule.fileRenderers` contributions carry their extensions, and the server's `WebModule.fileRenderers`, `WebModule.pageRemovals` and `WebModule.agentTabs` slots are gone

[中文版](2026-10-04-plugin-web-modules.zh.md)

A plugin package can now carry modules that run in the web app, with code, written the way the app's own modules are. All three examples are web modules now: the music example's audio player moved out of the web app into the plugin, the hello example's page is a React component the plugin ships, and the page removal example is a web module whose effect is all data.

## Details

- A plugin module states nothing about where it runs: `scripts/gen-ifaces.mjs` derives its host from its wiring and writes `side`, `source` and, for every web module, its built `file` into the package's `ifaces.json`. The hosts a module's wiring names are those of its requirements keyed by a host package (`@prismshadow/penguin-web#…`, `@prismshadow/penguin-server#…`) and of the modules its contributions, `from` and replacement name, where exactly one of the two host tables (`packages/{server,web}/src/ifaces.json`, read and never regenerated by a plugin build; a missing one is a build error saying how to generate it) carries that module. One host is the module's host; both are a build error naming the two wirings; none is the platform. One source file holding modules of both hosts is a build error, as is a web module requiring an interface its own package restates (it must import the web app's declaration). Every plugin package that runs gen-ifaces lists `@prismshadow/penguin-web` as a dev dependency, so a workspace build generates both host tables before it.
- `scripts/build-plugin.mjs` builds a package from that table: the main entry for Node lists the platform modules only; each web module becomes `dist/web/<Module>.js`, an ES module for the browser with lazily imported code split into chunks; `src/styles.css`, when present, is compiled by Tailwind into `dist/web/styles.css`, against the web app's theme as a reference. A web module shares the web app's React, JSX runtime, kernel runtime entry (`@prismshadow/penguin-core/kernel/runtime`, also serving `@prismshadow/penguin-core/plugin`) and the UI package's plugin surface (the page puts them on `globalThis.__penguinShared`, the build resolves those imports to it); bundling a copy of any of them, another package of theirs (the full kernel included) or a Node builtin fails the build. The UI surface is the explicit list in `packages/web/src/plugins/ui-surface.ts`, all of it already in the app's entry bundle: the page imports it statically, and the build resolves `@prismshadow/penguin-ui` to a stub exporting exactly those names, so importing another fails the build. A module whose class is empty still gets its file. The builtin plugins' pack cache key includes the plugin-facing types, the UI surface and the host tables' hashes. A stylesheet must name its Tailwind prefix on the theme import; a compiled class outside it fails the build, and so do two plugins built together (`scripts/build-plugins.mjs`) with one prefix.
- `GET /api/contributions` forwards the enabled plugins' web modules as `webModules`: each package's name and version, its web manifests, its interface and type entries, and the URLs of its built files and stylesheet. The files are served at `/api/plugins/<package>/web/<build>/<file>`, where the build id hashes the built files, with a year-long immutable cache; another build id answers 404.
- The web app asks for the list at boot, side by side with the install reconcile and `GET /api/me` (bounded at 3 s, nothing in safe mode); nothing of it is kept across loads. Packages are taken in package-name order. Each package's table is verified once per content (the kernel's full check, loaded only for a table not verified before, its verdict kept under a hash the page computes over what it checked); each verified package's files and stylesheets then load within a 4 s deadline, and the tree boots with all of them in one identity check through the kernel's runtime entry, so a page whose plugins were all verified before loads no arktype. Only when that boot fails are the packages tried in turn, so one that does not wire is left out alone. A package that fails to verify, load in time, wire or boot is left out with the reason, logged and shown on the Plugins page; the app boots without it. A sign-in after a load refused for want of a session reloads once, as does the first answer forwarding plugin modules once safe mode is left after a safe-mode load, and entering safe mode while plugin modules are assembled; a plugin enabled or removed elsewhere joins on the next load.
- Every `<Deferred>` boundary catches whatever is thrown below it: a chunk that does not arrive (the app's or a plugin's, such as one rebuilt under an open tab) shows the load notice with a Retry that reloads, and a component that throws while rendering shows "this part failed" with a Retry that remounts it. Plugin pages, session tabs, shell layers and each reply file renderer render under one, so a failing plugin component degrades its own block only.
- A reply's file renderers come from `ChatModule.fileRenderers` contributions alone: each carries its extensions as data and its component as code, and is drawn under its own `<Deferred>`. A renderer is handed the file (`url`, `path`, `name`); the interface language comes through `Language`.
- The shell gains a `ShellModule.pageRemovals` slot (`{ key }`, data only). The pages it names are dropped from the first render, with the routes under their paths and the pages under them; the pages home leads to stay. The server's `WebModule.pageRemovals` slot and the `pageRemovals` field of the contributions answer were removed.
- `packages/web/src/plugin-types.ts` holds what a plugin's web module may name of the web app at compile time, imported as types only: `FileRendererProps`, and `Language`, the interface language, which the settings module provides for a plugin module to `@Use`. `Language` is a store — `get()` returns the committed value and `subscribe` calls back once per change — the shape for every piece of app state offered to a plugin; the web app's language now lives in one such store (`state/locale-store.ts`), changed only by the setter and the browser's `languagechange`, never during render. The web package exports it as the types-only subpath `@prismshadow/penguin-web/plugin-types`; the example plugins list the web package as a devDependency.
- `scripts/verify-builtin-tree.mjs` runs the page's boot check (`checkExact`) over the builtin tree after the full check, so a tree the page would refuse fails the web build.
- A plugin page's component may be lazy: its code loads when the page is first opened, inside the shell's page boundary.
- A `ShellModule.pages` contribution's `order`, `admin` and `released` are optional. A page that states no `order` is placed after the pages that do, in slot order (plugin modules after the app's, by package name), so under a parent it follows the app's own children; `admin` defaults to false and `released` to true.
- `plugins/example-hello-page` is a web module contributing a page to `ShellModule.pages` under the Evaluation Center, stating no place, admin gate or release, drawn by its own lazy component in the app's page frame, in the interface language it subscribes to through `Language` (a switch re-draws it without a reload) and styled by its own `hp:` sheet. Its iframe document (`ui/`) was removed.
- `plugins/example-no-evaluation-center` is a web module with an empty class contributing `{ key: "benchmark" }` to `ShellModule.pageRemovals`. With both enabled, the hello page goes with the Evaluation Center.
- The web e2e suite's second plugin set, `all-examples`, enables all three examples.
- `plugins/example-music` is a web module contributing the audio player (card, seek bar, clock, its states and its words in both languages, following the interface language it reads through `Language`; until the file's length is known the clock reads `-:--` and the playhead waits at the start, and a length under a second reads `0:01`), styled by its own sheet whose utilities carry an `mp:` prefix, so none shares a selector with the host's. The web app's `features/audio/` and `AudioModule` were removed, as were the server's `WebModule.fileRenderers` slot, the `fileRenderers` field of the contributions answer and the web app's name-based renderer lookup.

## Compatibility

- A module contributing to the server's `WebModule.fileRenderers` slot no longer fits the platform's tree. Contribute a web module to `ChatModule.fileRenderers` instead, with `extensions` in the contribution's data and the component bound with `@Bind`.
- `ChatModule.fileRenderers` contributions carry `extensions` instead of `name`.
- A module contributing to the server's `WebModule.pageRemovals` slot no longer fits the platform's tree. Contribute a web module to `ShellModule.pageRemovals` instead, with the same `{ key }`.
- The server's `WebModule.agentTabs` slot, which nothing read, and the `agentTabs` field of the contributions answer were removed; a module contributing to it no longer fits the platform's tree.
