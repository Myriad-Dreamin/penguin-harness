# 连接了机器时，页面加载不再等待不需要的往返

- **Date:** 2026-10-04
- **Type:** fix
- **Scope:** `server`, `web`

[English](2026-10-04-load-speed-fixes.md)

这批改动减少了打开 Web App 及其公司页面时的请求、往返与重复工作，其中若干项主要在慢速链路上才感受得到。

## 细节

- 经 `/server/<id>/api/…` 转发到机器的请求，复用经该机器 ssh 会话建立的通道，不再每个请求新拨一条——此前每次调用都因此多付一次往返。通道只在建立它的那个会话内复用：会话被替换时，旧会话的通道会在下一个请求之前关闭。若一次读取拿到的保活通道恰好刚被机器关闭，会在新通道上重发一次；写入不重发。
- Session 列表的首次加载不再等待它请求的每一份列表：既不等已连接的机器，也不等每个 Agent 的列表（其中包括组织的每位员工）。已回答的列表（尚未回答的机器以其上次记住的 Session 代替）随到随显示，持有某个 Session 的列表一回答，该 Session 即可打开；其余列表到达后再并入。聊天页在判定链接所指的 Session 不存在、或挑选最近一次对话之前，仍会等完整列表。
- 终端列表可经 API socket 正常应答。此前每次加载都返回 401：终端路由读取的是 session cookie，而 socket 调用不携带 cookie；页面随后还要再发一次 `GET /api/me` 确认自己是否仍处于登录状态。
- 页面挂载时读取用户偏好或 Project 模型列表的多个部分，在请求进行中时共用同一个请求，不再各发一份：此前一次加载要发五到六次 `GET /api/me/prefs`、两次模型列表。请求结束后不保留任何结果；写入之前发出的读取，也不会交给写入之后才发起的调用方。
- 通过 URL 打开的组织页面会立即读取该 Project 的组织列表，不再先等待 Project 列表。
- 内核的 manifest 文档类型改为首次使用时才构建，不再在导入内核时构建——Web 每次加载都会导入内核，却从不使用这个类型。
- 消息时间改用按界面语言复用的同一个格式化器。
- 组织页面的读取不再把未变化的值班与工单行重写进 SQLite；trace 索引扫描也不再重写大小未变的分片。
- Session 列表与组织列表保存在浏览器中（`localStorage`，按数据根、用户与 Project 区分；登出时清除），下次加载时在服务器回答之前即从中绘制：侧栏立即显示上次已知的行；路由指向的 Session（包括值班与工单 Session）无需等待列表即可打开并请求其消息；通过 URL 打开的组织页面无需等待组织列表即知道该向哪台机器发请求。服务器回答后替换所绘制的列表，变化的行以短暂过渡收束（保留的行滑到新位置，新行淡入，移除的行合拢；减少动态效果时不做动画）。不依据所绘制的列表下任何结论：报告 Session 或组织不存在、挑选最近一次对话、显示“暂无 Session”，都只在服务器回答之后。每份列表的上限：每个 Agent 每台服务器 30 条活跃行、每个 Project 20 个组织 Session、100 个组织。安全模式下不读取。各机器上次记住的 Session 也改存于同一缓存；早期版本按机器保存的条目会被移除，见[向后兼容](2026-10-04-backward-compatibility.zh.md)。
